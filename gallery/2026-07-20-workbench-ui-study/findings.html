Workbench UI vs Custom UI

A UX design study for T.N.A.'s arcane worktable: when to reuse the vanilla crafting-grid screen (the one crafting tables never change) and when a custom UI earns its keep. Idioms & public docs only — no mod code or pixels used.
The one tension. "The crafting table never changes its UI" is a stability contract, not laziness: recipes are matched server-side against the container, so the 3×3 screen can stay frozen forever while content grows without bound. Because slot indices mean fixed things (0 = result, 1–9 = grid), the recipe book, JEI/REI "+" auto-fill, and shift-click all work for free. Every step away from that standard shape buys expressive power (cost meters, a wand slot, previews) and costs you that free infrastructure — which you then owe by hand. The whole decision is: does my crafting concept truly need shapes/axes the grid can't hold, and will I pay to rebuild the parity I'm discarding?
1 · Why the crafting table never changes its UI (the contract)

Minecraft splits every container into a server-side AbstractContainerMenu (which slots exist, quick-move, recipe resolution) and a client AbstractContainerScreen (rendering only). CraftingMenu fixes the layout: index 0 = result, 1–9 = the 3×3 grid, then inventory + hotbar. The player inventory's 2×2 is the same shape minus the outer ring.

The UI is frozen on purpose:

  • Recipes are decoupled from the screen. Shaped, shapeless, and special recipes are all matched by RecipeManager against the container. The screen never knows which kind it is — it only shows "grid in, one result out." Adding a recipe never touches the UI, so one screen renders every recipe that will ever exist.
  • One result slot, one behavior. Taking the output runs fixed ResultSlot logic; muscle memory transfers across every table-like block.
  • The recipe book plugs into a known shape via RecipeBookMenu hooks that address the grid by fixed indices.

So invariance is a guarantee: because recipes, the recipe book, JEI/REI, and quick-move all address a fixed slot shape, the screen can stay frozen while the game grows. A player who learned the grid in 2011 still knows it.

2 · The reuse family — mods that keep the grid, and why

These change where/when/how-fast you craft, not how — so they keep vanilla CraftingMenu and inherit JEI, the recipe book, and quick-move for free.

  • FastWorkbench / FastBench — pure performance: caches the last matched recipe. Not a UI mod at all; keeping the vanilla menu is the compatibility surface.
  • Crafting Station / Visual Workbench — keep ingredients in the grid after close, pull from neighbors, render on the block. The feature is container behavior + world render, not slot layout.
  • Portable / backpack crafting (Sophisticated Backpacks' Crafting Upgrade, etc.) — open the ordinary 3×3 with no placed block. Changes context, not interaction.
  • Quark tweaks — leave the screen vanilla, tweak behavior around it; touching the screen would forfeit the recipe book + JEI hooks.

Instructive counter-example — Extended Crafting's Basic Table

A 3×3 visually, but a separate recipe pool that rejects vanilla recipes — to keep progression tiers from collapsing into vanilla. Proof that "3×3 grid shape" and "vanilla recipe contract" are separable: it kept the shape for familiarity but broke the contract on purpose, paying the compat cost knowingly (and scaling to 5×5/7×7/9×9 above).

Reuse is right when the feature is orthogonal to the interaction — performance, persistence, portability, neighbor-pulling, cosmetic variants. The tell: if it's expressible as container behavior, keep the screen. The moment it needs new slots, new dimensions, or new on-screen widgets, you're forced custom.

4 · The forcing functions — what pushes a design off the grid

Every custom UI above clusters around a small set of things the 3×3 structurally cannot express. A mod diverges when it needs one of:

Resource axis

A magical energy/fuel/power to show and spend — vis, mana, starlight, essence, souls, RF. The grid is resourceless.

Tool / battery slot

A persistent object the craft draws from, not of — wand, Tartaric gem, impetus.

Cost / validity readout

Show the price & legality before commit; reject illegal states; gate on research / tier / reputation.

Non-grid shape

Bigger than 3×3, ordered sequences where position means something, or typed stat-bearing components.

Time / charge

Recipes that accumulate over ticks → need a progress or fill display.

Browse / search

Network inventories, buildable-item lists, upgrade tabs — navigation at scale.

Not "item from shape"

A ritual, transform, summon, or ward — no grid metaphor applies.

In-world payoff

Externalizing to placed blocks/dropped items = fiction + native automation + decoration (costs discoverability).

Per-craft config

A choice that isn't an ingredient — a mode toggle, a constellation, side routing.

And a 10th that's really a side effect: the UI doubles as the progression display — slot count, tabs, or tiers that visibly grow with advancement (Astral, Tinkers).

5 · The hidden bill — JEI/REI parity you throw away going custom

The most underestimated cost. What the vanilla-shaped grid gives free vs what breaks:

CapabilityVanilla gridCustom menu
Recipes appear in JEI/REIfree (vanilla Crafting category) invisible until you write a plugin
"+" recipe transfer / auto-fillfree (built-in handler) dies — extra/ghost slots unrecognized; write IRecipeTransferHandler
Vanilla recipe bookfree via RecipeBookMenu gone unless you re-implement its hooks
Shift-click / quick-moveinherited conventions hand-write quickMoveStack without duping
Universal mod-recipe compatany datapack recipe just works your recipe type only, plus a catalyst registration

To restore parity you owe, realistically: a JEI plugin and an REI plugin, a recipe category (draws the cost/aspects in the lookup panel), a transfer handler (for ghost/battery slots, that means a validated C2S packet — client viewers can't move server items), and catalyst registration. Budget that as part of the "go custom" decision, not a nice-to-have follow-up.

6 · The decision checklist + smell tests

Reuse the vanilla grid IF

  • Crafting is genuinely 3×3 shaped/shapeless with no cost the player must see.
  • You want recipe-book + JEI/REI auto-fill free, zero plugin work.
  • The "magic" is in the ingredients & outputs, not the act of crafting.
  • No new per-craft resource axis, no non-grid shape, no preview step.

Add an arcane overlay (grid + readout) IF default for an arcane workbench

  • Still grid-shaped, but a cost/requirement (vis/aspects) must be shown and can gate the craft.
  • A non-consumed tool (wand/focus) participates without joining the recipe.
  • You want the arcane fantasy legible while keeping muscle memory + most parity.
  • The new mechanic is a modifier on grid crafting — chips/bars/labels around an unchanged grid.

Go fully custom IF (need ≥1) — and you've budgeted the full stack

  • The recipe shape isn't a grid (radial, node-graph, pedestal-orbit, sequential).
  • A resource axis must be interactively manipulated, not just displayed.
  • Validity/cost is a live-recomputing feedback surface central to the interaction.
  • You need search/category browsing of a large set (research tree, spell builder).
  • You need preview-then-commit.

Smell tests — signs you picked wrong

  • Reskin sin: your custom screen is a 3×3 with a prettier background and nothing else → you broke the recipe book + "+" for zero gain. Revert to grid/overlay.
  • Can't name the mechanic the grid couldn't hold in one sentence → don't go custom.
  • Recipe JSON grew parallel fields (cost, aspects, tool) explained in the tooltip/wiki instead of the UI → the mechanic wants an overlay.
  • Cost readout only updates on reopen → you're not recomputing on slot change / not syncing.
  • A failed craft gives no reason → add the "why" tooltip.
  • Empty arcane slots look identical to grid slots → add ghost hints/labels.

Recommendation for the T.N.A. arcane worktable

Grid + arcane overlay — augment, don't replace. Keep a real vanilla-shaped 3×3 + result slot (so vanilla recipes work and JEI/recipe-book largely survive), then decorate the frame with exactly the two things Thaumcraft's Arcane Workbench added:

  • A wand/focus slot off to the side, with a ghost-wand hint in the empty state.
  • A ring of aspect/vis cost chips that appear only when the recipe needs them and live-recompute on every slot change; the result slot locks (with a "why" tooltip — "Requires 12 Vis, chunk has 4") when unaffordable.

This matches the 3×3 grid top face we just shipped in the texture pass — the block's exterior and its screen now tell the same story. It also reuses what the repo already has: the Arcane Orrery's menu+screen+sync stack, the dark-purple UI palette (0xF0100A18 / 0xE8D9FF), the C2S-validation checklist for the craft packet, and data-components for wand vis / research state.

Deliberately NOT fully custom for the worktable — a bespoke screen that's just a reskinned grid is the cardinal sin. Reserve fully-custom for the systems that are genuinely a different shape: infusion (central pedestal + orbiting input pedestals, in-world), the research web (node-and-line browser, search), and essentia handling (fill columns + tier trim). Those earn their custom UIs; the crafting worktable does not.
